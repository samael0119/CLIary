今天选择一个实际可靠性缺陷：统计用 `COALESCE(tool_id, executable)` 分组，但在 Catalog 已无该 ID 时，首次使用查询只按 `executable=ID` 查找。工具 ID 与命令名不同（如 `bottom / btm`、`httpie / http`、`typescript / tsc`）时，查询得到 NULL，读取整数导致整个统计请求失败。首页、历史页、统计页均依赖这一统计方法，受到同一错误影响。

另一个同源症状是：按已移除的旧工具 ID 查询历史返回零，尽管记录仍存在。有效的私有命令若恰好与 Catalog ID 同名，也可能使首次使用查询和历史查询漏掉自己的记录。

已有的历史引导解决的是无数据时如何采集；本轮解决有真实数据时错误或假零的问题，优先级高于新的外观素材或引入模型依赖。只修复记录键与查询条件不一致这一问题，不重做此前页面或年报。

## 改动与收益

1. 历史查询保留原来的当前 Catalog 解析，同时显式匹配输入对应的已保存工具 ID 和实际可执行名称。旧 ID 即使不再被 Catalog 收录，或名称解析已指向新条目，仍可找到历史。
2. 统计的首次记录查询在有／无 Catalog 元数据的两条路径都匹配已持久化的统计键（工具 ID 或可执行名称），并保留原有当前可执行别名匹配。统计不会因条目移除而读取空的 `MIN(timestamp)`，也不会把旧调用重新算作当期首次使用。
3. 使用现有参数绑定与索引，无数据库迁移、新依赖或额外事件写入。没有通过捕获错误、默认零值或过滤旧 ID 来掩盖数据问题。
4. JSON 字段、现有分组口径、已识别工具的别名查询和时间范围保持兼容。未知／移除记录保留在排行榜、总量、活跃天数与月度统计中；无匹配记录仍返回真实零值和空首末时间。
5. README 说明旧 ID / 实际命令名查询、首次记录时间来源，以及不重写或追溯合并历史的边界。

## 剩余边界与风险

- 历史仍按保存的 ID／命令名统计；工具重命名或从未知变为已识别后，不自动重写、合并历史身份。本轮只保证记录可查、统计不会因记录键漏查而报错。
- 查询沿用当前 Catalog 别名，并补充精确记录匹配；名称歧义可能汇总多个匹配来源，不引入新的身份消歧系统。类别仍反映当前 Catalog，旧条目无匹配时显示未分类，不虚构历史元数据。
- 本轮不是整个 Catalog 更新兼容性的修复。现有收藏 API 对已移除条目会报错，可能另外影响收藏页／首页；已记录为独立后续问题，当前 HTTP 检查的临时数据没有收藏这些移除条目。
- 首次使用仍逐工具查询，未在这次可靠性修复中重写统计性能架构；非常大的历史库可另行评估。
- 各每日分支尚未合并，共享的 Core 历史模块、测试与 README 可能需要合并时处理交叉改动；今日未做自动集成。
