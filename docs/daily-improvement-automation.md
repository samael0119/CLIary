## 任务说明

在 `/home/hyh/Projects/CLIary` 完成今天最值得做的一项改进。

先查看当前代码、已有问题和下面的候选需求，判断哪一项能在今天完成一轮完整、有明确收益的改进。候选需求不限定选择范围；发现更重要的新问题时可以优先处理。不要为了改代码而改代码。如果没有值得实施且可完整验证的改进，说明原因并结束，不创建空提交。

优先考虑性能、可靠性、可维护性、测试覆盖和明显的用户体验问题。一天只处理一个问题，明确改进前的症状、改动后的收益，以及验证方式。不要同时顺手实现其他需求。

候选需求按主题合并，便于判断优先级；较大的主题可以先选择其中一个能完整实现并验证的切入点，不把整个主题提前标记为完成。

开始修改前，从当前 `main` 创建当天独立的分支，命名为 `improve/YYYY-MM-DD-主题`；不要直接在 `main` 修改。如果工作区已有未提交修改或同名分支，不要覆盖，先报告冲突。完成后运行与改动相关的检查，提交到该分支并推送到私有仓库，保留 `main` 供用户审阅和合并。若推送受权限或网络限制，保留本地提交并说明原因。不要自动合并。

报告当天选择的问题、选择理由、关键改动、验证结果、分支名和提交号；如有剩余风险，也要说明。遵循仓库中的 `AGENTS.md` 指令。最终总结使用中文。

### 候选需求

1. **环境感知的工具识别**：扫描系统 `PATH`，并识别常见开发语言环境变量指向的工具或安装目录，覆盖 Java、Go、Rust、Python、Node.js、Ruby、PHP、.NET 等生态及常见版本管理器；示例不作为范围上限，按实际目录约定补全。变量名需核实，例如 Go 使用 `GOROOT`。避免把“未扫描”误判为“未安装”。
2. **已安装工具的筛选与分类**：为已安装工具页面提供实用筛选；调查未识别工具能否按来源、归属或安装目录归类；细化现有类别，并在确有浏览收益时支持多级目录。
3. **工具比较质量**：完善结构化比较的字段、差异说明和使用场景，确保信息来自 Catalog 或其他可核实来源。
4. **工具 Logo 与视觉素材**：改善工具识别度；若使用开源网站的 Logo，先核对来源、许可、商标使用和署名要求。
5. **历史与统计的可用性**：调查页面为空是缺少采集数据、尚未使用，还是功能缺口；改善数据链路或空状态，让用户知道如何产生可用数据。默认仅记录工具级信息，保护隐私。
6. **CLIary Wrapped 年度回顾**：结合先前里程碑 2 的目标与 PRD，逐步实现 `cliary wrapped [year]` 与 Web 年报。优先用真实 History 数据计算年度总量、活跃天数、常用工具、月度趋势等；年度新宠、被遗忘的收藏、使用习惯变化等特殊统计也必须有数据依据。数据不足时提供准确的空状态，不编造回顾。
7. **可选的本地大模型能力**：核实当前缺口，选择一个能验证收益的最小场景接入本地推理，例如语义／跨语言搜索、自然语言查询、比较摘要或年报摘要。模型不可用或用户关闭 AI 时，搜索、浏览、比较、安装识别、历史、统计和年报仍需正常工作；工具事实始终以结构化 Catalog 为准，不由模型生成安装命令、版本、许可证等事实。

每天重新评估优先级，不预先按上述顺序分配需求。
